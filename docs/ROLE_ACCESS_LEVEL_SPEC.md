# アクセスレベル導入仕様書

## 1. 背景と目的
現在の権限システムでは、特定の機能権限（例：ユーザー管理の編集権限）を持っている場合、システム管理者などの上位権限者に対しても操作が可能となってしまう「権限の逆転」が発生する可能性があります。
これを防ぐため、ロール自体に「アクセスレベル（ランク）」を設定し、厳格な階層構造によるアクセス制御を導入します。

## 2. アクセスレベル定義
0から4までの5段階のレベルを定義します。数字が大きいほど権限が強くなります。

| レベル | 名称 | 想定される役割 | 説明 |
| :--- | :--- | :--- | :--- |
| **4** | **システム管理者** (System Admin) | SUPER_ADMIN | システム全体の全権限を持つ。自分より下位の管理者を含む全ユーザーを管理可能。 |
| **3** | **上級管理者** (Senior Admin) | 部長・エリアマネージャー | マネージャー層を管理可能だが、システム管理者には干渉できない。 |
| **2** | **管理者** (Manager) | MANAGER | 一般スタッフやリーダーを管理可能。 |
| **1** | **リーダー** (Leader) | チームリーダー・主任 | 現場レベルの管理。一般スタッフよりは上位。 |
| **0** | **一般** (General) | STAFF | 一般ユーザー。管理権限は持たない（基本値）。 |

## 3. データベース変更
`CustomRole` モデルに `rank` フィールドを追加します。

```prisma
model CustomRole {
  id          String   @id @default(cuid())
  name        String   @unique
  displayName String
  isSystem    Boolean  @default(false)
  permissions Json     // 既存
  pageAccess  Json?    // 既存
  rank        Int      @default(0) // ★新規追加: アクセスレベル (0-4)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  users       User[]
}
```

## 4. 制御ロジック（セキュリティルール）

### 4.1. ユーザー操作（編集・削除・パスワードリセットなど）
**ルール: 操作実行者のランク > 操作対象者のランク**

*   自分より**アクセスレベルが低い**ユーザーに対してのみ、管理権限を行使できます。
*   自分と**同ランク**または**上位ランク**のユーザーに対しては、たとえ「ユーザー編集権限」を持っていても操作できません。
*   ※自分自身の編集は例外的に許可（プロフィールの更新など）。

### 4.2. ロール操作（ロール割当・作成）
**ルール: 割当・設定可能なランク <= 自分のランク**

*   自分より高いランクを持つロールを、他者に割り当てることはできません。
*   自分より高いランクを持つロールを作成・編集することはできません。

## 5. 既存ロールへの適用計画（マイグレーション）

既存のロールに対して、以下の通りランクを割り当てます。

*   **SUPER_ADMIN**: 4 (システム管理者)
*   **MANAGER**: 2 (管理者)
*   **PARTNER_MANAGER**: 1 (パートナー管理者/リーダー相当)
*   **STAFF**: 0 (一般)
*   **PARTNER_STAFF**: 0 (一般)

## 6. 実装ステップ

1.  **DBスキーマ更新**: `prisma/schema.prisma` へのフィールド追加とマイグレーション実行。
2.  **データ移行**: 既存ロールへのランク設定スクリプトの作成と実行。
3.  **APIロジック実装**:
    *   ユーザー編集API等にランク比較ロジックを追加。
    *   権限チェックユーティリティ (`src/lib/permissions.ts`) の拡張。
4.  **UI更新**:
    *   ロール管理画面でランク（0-4）を選択・表示できるように変更。
    *   ユーザー一覧画面で、操作不能なユーザー（同格以上）の編集ボタンを非表示/無効化。
